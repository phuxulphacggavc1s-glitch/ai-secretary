# 企业微信 AI 秘书主动互动闭环设计

## 1. 目标

将 AI 秘书的主动消息统一发送到企业微信自建应用，并补齐“主动询问 -> 用户回复 -> 自动更新任务 -> 安排下一次跟进”的闭环。在不频繁打扰用户的前提下，让秘书能够结合任务、对话记忆和长期画像给出具体建议。

本期采用单用户优先、可平滑扩展到多用户的设计。所有用户定位仍通过 `WECOM_APP_USER_MAP` 完成，不在代码中写死企业微信账号或 Supabase UUID。

## 2. 范围

### 2.1 本期包含

- 晨报、到期提醒、隔日追问、S 级二次提醒和风险晚报统一走企业微信自建应用消息。
- 每次主动消息记录发送原因、关联任务、发送结果和回复状态。
- 用户回复任务追问时，AI 自动判断任务是已完成、推进中、等待回复还是被卡住。
- 自动保存进展说明、下一步动作和下一次跟进时间。
- 结合任务简报、最近对话和长期记忆生成晨间建议与风险晚报。
- 安静时段、每日总量、同一任务频率和失败重试保护。
- 所有新增数据库查询显式按 `user_id` 过滤。

### 2.2 本期不包含

- 语音、图片和文件消息理解。
- 同一条消息同时更新多个任务。
- 自主替用户联系客户、供应商或其他企业微信成员。
- 无需确认的高风险操作，例如删除任务、发送外部消息或修改重要业务数据。
- 完整多员工权限管理界面。

## 3. 方案选择

采用“秘书外联记录”方案。每一次主动联系都形成一条可追踪记录，而不是仅依靠 AI 从全部任务中猜测用户在回复哪一件事。

不采用纯内存会话，因为服务重启后会丢失上下文；不采用纯 AI 猜测，因为多个任务同时存在时容易误改；不直接复用群机器人 Webhook，因为它无法稳定形成个人双向对话闭环。

## 4. 架构

### 4.1 统一发送入口

新增面向业务的发送服务 `send_secretary_message(user_id, content, kind, task_id=None)`：

1. 从 `WECOM_APP_USER_MAP` 反查 Supabase 用户对应的企业微信成员账号。
2. 调用现有 `send_app_text()` 发送自建应用文本消息。
3. 把成功、失败和失败原因写入外联记录。
4. 发送失败时返回明确失败结果，调度程序不得把失败当作已送达。

晨报、催办和晚报只调用这一入口。现有群机器人服务保留给历史功能，但不再承担本期个人秘书的主动消息。

### 4.2 外联记录表

新增 `secretary_outreach` 表：

| 字段 | 用途 |
| --- | --- |
| `id` | UUID 主键 |
| `user_id` | Supabase 用户 ID，必填 |
| `task_id` | 关联任务，可为空 |
| `kind` | `morning_briefing`、`task_followup`、`s_escalation`、`evening_review` |
| `content` | 实际发送内容 |
| `status` | `pending`、`sent`、`failed`、`replied`、`expired` |
| `wecom_userid` | 实际接收的企业微信成员账号 |
| `failure_reason` | 发送失败原因，可为空 |
| `sent_at` | 成功发送时间 |
| `replied_at` | 用户有效回复时间 |
| `created_at` | 创建时间 |

表启用 RLS，并创建 `user_id + created_at`、`task_id + status` 索引。后端使用 service key 时，所有读取和更新都显式添加 `user_id` 条件。

### 4.3 主动消息调度

采用“适中型”规则：

- 08:30：发送晨间重点与 1 条具体建议。
- 08:00-21:00：每分钟扫描到期跟进，但每位用户一次只发送一项最重要任务。
- 隔日追问：任务没有形成最终结果时，下一次跟进默认延后一天。
- 20:00：S 级任务仍未完成且当天没有有效回复时，发送一次二次确认。
- 19:30：仅当存在逾期、等待超时或受阻事项，并且最近三小时没有主动联系时，发送风险晚报。
- 21:00-次日 08:00：禁止主动发送；到期消息顺延到次日允许时段。
- 每人每天最多 4 条主动消息。
- 同一任务每天最多主动追问 1 次，S 级晚间二次确认除外。
- 当天没有风险事项时不发送晚报。

每日限制以 `secretary_outreach` 中当天 `sent`/`replied` 记录计算，不依赖进程内计数，因此服务重启不会清零。

## 5. 用户回复闭环

企业微信收到文本后按以下顺序处理：

1. 校验签名、解密消息、完成用户映射。
2. 查询该用户最近一条尚未回复且未过期的任务外联记录。
3. AI 在三个意图中判断：`create_task`、`task_progress`、`chat`。
4. 明确是新待办时，新建任务，不影响旧任务外联记录。
5. 明确是任务进展时，调用现有 `judge_reply()` 更新关联任务，并把外联记录标记为 `replied`。
6. 普通聊天时继续调用现有 `chat()`，保留未回复的任务上下文。
7. 无法确定是否在回复任务时，只追问确认，不修改任务。

任务进展回复示例：

- “完成了” -> `done`，清空下一次跟进时间。
- “客户说周五回复” -> `waiting_response`，提取周五为下一次跟进时间。
- “缺报价表，卡住了” -> `blocked`，记录阻塞原因和下一步动作。
- “正在做，明天给你结果” -> `in_progress`，安排明天跟进。

任何任务更新都必须使用 `.eq("id", task_id).eq("user_id", user_id)`；任务事件同时记录原状态、新状态、用户原话和 AI 判断来源。

## 6. 主动建议

晨间建议输入包括：今日任务、逾期任务、等待回复超时、受阻任务、最近对话和长期画像。输出限制为：

- 先指出最重要的 1-2 件事。
- 给出一条可以立即执行的建议。
- 有需要用户拍板的事项时直接提问。
- 不超过 150 字，不使用空泛鼓励。

风险晚报只针对未解决风险，不重复晨报内容。它应说明“什么还没有结果、风险在哪里、建议下一步做什么”，最多列出 3 项。

建议生成失败时使用确定性模板降级；发送失败必须记录错误，不得静默忽略。

## 7. 误判和打扰保护

- 任务外联上下文默认 36 小时后过期，过期回复按普通聊天处理。
- 只有 `task_followup` 和 `s_escalation` 可以触发任务状态更新。
- 晨报和晚报后的回复默认进入普通聊天，除非用户明确提及某项任务。
- AI 返回非法状态、非法时间或缺少关联任务时，不更新数据库，并给用户明确提示。
- 同一条企业微信消息通过消息 ID 做幂等保护，避免回调重试造成重复任务或重复更新。
- 主动发送失败不推进 `next_follow_time`；成功后才计算下一次跟进。
- 用户说“别催这件事了”时只暂停该任务的跟进，不删除任务。

## 8. 数据安全

- Secret、Token、AESKey 只保存在服务器环境变量，不写入数据库、日志或代码。
- 日志不得输出 access token、完整回调密文或环境变量内容。
- `tasks`、`users`、`secretary_messages`、`secretary_outreach` 的查询与更新全部按当前 `user_id` 限定。
- 企业微信账号和 Supabase 用户的绑定仅来自 `WECOM_APP_USER_MAP`。
- 对外回调继续使用签名校验和 AES 解密，不增加绕过鉴权的调试接口。

## 9. 错误处理

- 未配置自建应用：记录清晰错误，调度任务跳过，不回退到不受控通道。
- 用户未映射：不发送，并记录具体用户 ID 缺少映射。
- access token 过期：沿用现有刷新一次机制，仍失败则记录失败。
- DeepSeek 不可用：任务状态使用现有关键词降级判断；建议使用确定性模板。
- Supabase 写入失败：不声称任务已更新，并向企业微信发送“记录失败，请稍后再试”。
- 企业微信回调重复：返回成功但不重复处理业务。

## 10. 测试与验收

### 阶段 1：统一主动消息通道

- 晨报、普通催办和 S 级提醒全部调用自建应用发送服务。
- 未映射、发送失败、token 刷新均有测试。
- 线上用测试消息确认企业微信自建应用能主动收到消息。

### 阶段 2：任务回复闭环

- 催问后回复“完成了”，正确更新被催问任务，其他任务不变。
- 回复“客户周五答复”，状态和下一次跟进时间正确。
- 普通聊天和新建待办不会误改被催问任务。
- 模糊回复只追问确认，不更新任务。
- 重复回调只处理一次。

### 阶段 3：适中型建议策略

- 安静时段不发送。
- 每日第 5 条主动消息被跳过并记录原因。
- 同一普通任务当天不会催两次。
- 无风险事项不发晚报。
- 有逾期、等待超时或受阻事项时，建议内容包含具体下一步。

每个阶段都先写失败测试，再实现最小改动；阶段测试和完整后端测试通过后才能部署下一阶段。

## 11. 部署顺序

1. 备份服务器环境变量和当前提交号。
2. 部署数据库升级脚本，确认 `secretary_outreach` 表、索引和 RLS 正常。
3. 部署阶段 1，验证主动应用消息。
4. 部署阶段 2，人工完成四类回复验收。
5. 部署阶段 3，观察至少一个工作日的限频与建议质量。
6. 保留旧群机器人配置一周作为人工回滚参考，但新流程不调用它。

涉及企业微信后台配置的具体步骤必须在部署当日重新核对官方文档。本设计编写时官方开发文档页面无法从当前环境正常读取，因此不把未经核实的后台菜单路径写入设计。

⚠️ 企业微信后台操作步骤尚未经官方文档核实，操作时如遇界面或流程不符，先停下确认，不要硬做。
